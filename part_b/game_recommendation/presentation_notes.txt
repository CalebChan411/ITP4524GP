SLIDE 07 - Model 02: match the content
------------------------------------------------------------
Suggested speaker B | Target 0:50

CORE TALK
Model Two uses game tags and genres. This follows the content-based approach in Lecture Nine. We use TF-IDF to turn the tags into numbers. A less common tag can receive more weight. We learn these weights from training games. Then we add the vectors of the user's known games. We set the result to unit length. This gives us a user profile. Cosine similarity compares that profile with each game vector. A higher match gives a higher score. This design uses game details to match interests. It does not need other players’ histories. TF-IDF also links to Lecture Eleven.

VISUAL CUE
Follow Describe → Encode → Build profile → Rank. Use the formula legend to identify the user profile and game vector.

EXTRA HELP
A vector is a list of numbers. Unit length keeps the comparison focused on direction. The cosine score is a ranking score, not a chance of liking the game.

SLIDE 08 - Model 03: add structured features
------------------------------------------------------------
Suggested speaker B | Target 0:55

CORE TALK
Model Three adds 11 numeric features to the tag model. They include price, approval, review count, release year, game modes and supported systems. We use log review count to reduce very large differences. We fill missing values using training medians. We scale the values between zero and one. We then set the numeric block to unit length. Next, we join the tag and numeric blocks. We compare two tag weights on validation: 0.50 and 0.75. The 0.50 setting gets higher Recall at Five. So we keep equal weight for the two blocks. This tests whether extra game details improve the tag-only model.

VISUAL CUE
Name the feature groups. Then follow fill → scale → join → rank. Use the validation bars to explain the chosen weight.

EXTRA HELP
Alpha is the tag-block weight. The code multiplies each block by the square root of its weight. All learned filling and scaling values come from training data.

SLIDE 09 - Model 04: learn from similar players
------------------------------------------------------------
Suggested speaker B | Target 1:00

CORE TALK
Model Four is user-based collaborative filtering. This is another method from Lecture Nine. We first build a user-by-game table. A one means the user has a positive play record. A zero means we did not observe one. We compare the user's play pattern with other players. Cosine similarity measures the match. We leave out the target user's own row. We keep up to 30 players with positive similarity. Closer players have more weight. Their game records give each unseen game a support score. Finally, we remove known games and rank the rest. Validation chose 30 neighbours rather than 10.

VISUAL CUE
Use the matrix to explain rows, columns, ones and zeros. Then explain find players → weight their plays → rank games.

EXTRA HELP
A zero is not a dislike. The 30 neighbours are a maximum. A player with zero similarity gives no support.

SLIDE 13 - What do Precision and Recall mean?
------------------------------------------------------------
Suggested speaker C | Target 1:10

CORE TALK
This example explains our metrics. The hidden test games are I and J. We recommend five games: I, K, L, M and N. Only I is a hit. Precision asks how much of the recommendation list matches the hidden answers. One hit out of five gives 20 percent. Recall asks how much of the hidden answer set we found. One hit out of two gives 50 percent. We calculate these values for each user, then take the average. Hit Rate counts users with at least one hit. Coverage counts how much of the game catalogue appears across all recommendation lists. These measures describe different parts of the result.

VISUAL CUE
Highlight I in both sets. Explain why the Precision denominator is five and the Recall denominator is two.

EXTRA HELP
These use the precision and recall ideas from Lecture Six for a ranked list. They measure matches to recorded plays. They do not measure satisfaction directly.

SLIDE 19 - Reflection: lessons and next steps
------------------------------------------------------------
Suggested speaker D | Target 1:00

CORE TALK
We learned to test our ideas against a strong simple baseline. We also learned to choose settings before checking the final test answers. Matching old game titles was a practical problem. We kept 111 reliable matches and skipped 89 unclear or unavailable titles. We handled missing prices and years with training medians and missing-value flags. Some limits remain. The play records have no timestamps. We need dated records and game details from the same period. We used one split, so future work should repeat the tests and show how much the results vary. We should also hold out whole users. That would test a true new-user case.
